= Meta-Circularity in NOSTR Gift Wrap
:toc:

== The Key Insight: Recursive Wrapping

Gift wrapping is **meta-circular** - you can wrap an Event in an Event, infinitely:

[source]
----
Event (kind 1)
  → Wrap → Event (kind 1059)
    → Wrap → Event (kind 1059)
      → Wrap → Event (kind 1059)
        → ...
----

== Why Event-to-Event is Correct

[source,go]
----
// This maintains meta-circularity
func Wrap(innerEvent *event.Event, ...) (*event.Event, error)

// Both input and output are *event.Event
// Can wrap the result again!
wrapped1 := nip59.Wrap(event, ...)      // Event → Event
wrapped2 := nip59.Wrap(wrapped1, ...)   // Event → Event (recursive!)
wrapped3 := nip59.Wrap(wrapped2, ...)   // Event → Event (recursive!)
----

== Why GiftWrap Type Would Break This

[source,go]
----
// This BREAKS meta-circularity
type GiftWrap struct {
    Inner    *event.Event
    Envelope *event.Event
}

func (gw *GiftWrap) Wrap() (*event.Event, error)

// Problem: Can't wrap a GiftWrap in a GiftWrap
gw1 := &GiftWrap{Inner: event}
envelope1 := gw1.Wrap()

// Now what? envelope1 is an Event, not a GiftWrap
// Lost the ability to recursively wrap
gw2 := &GiftWrap{Inner: envelope1}  // Works, but awkward
envelope2 := gw2.Wrap()

// vs. the elegant recursive version:
wrapped1 := nip59.Wrap(event, ...)
wrapped2 := nip59.Wrap(wrapped1, ...)  // Same function, recursive!
----

== Recursive Wrapping Use Cases

=== 1. Multi-Hop Privacy
[source]
----
Original Event (kind 1)
  → Wrap for Relay A → Event (kind 1059)
    → Wrap for Relay B → Event (kind 1059)
      → Wrap for Relay C → Event (kind 1059)

Each relay unwraps one layer, forwards the next
----

=== 2. Onion Routing
[source]
----
Message
  → Wrap for Node 3 (destination)
    → Wrap for Node 2 (middle)
      → Wrap for Node 1 (entry)

Each node unwraps, sees next hop
----

=== 3. Layered Encryption
[source]
----
Sensitive Event
  → Wrap for Inner Circle (team)
    → Wrap for Outer Circle (company)
      → Wrap for Public (anyone)

Different keys for different access levels
----

== The Correct Design

**Keep Event-to-Event transformation** to preserve meta-circularity:

[source,go]
----
// ✅ CORRECT: Maintains recursion
func Wrap(innerEvent *event.Event, senderPrivKey, recipientPubKey string) (*event.Event, error)
func Unwrap(envelope *event.Event, recipientPrivKey, senderPubKey string) (*event.Event, error)

// Usage: Recursive wrapping
layer1 := nip59.Wrap(event, key1, pub1)
layer2 := nip59.Wrap(layer1, key2, pub2)  // Same function!
layer3 := nip59.Wrap(layer2, key3, pub3)  // Same function!

// Unwrap in reverse
unwrap1 := nip59.Unwrap(layer3, key3, pub2)  // → layer2
unwrap2 := nip59.Unwrap(unwrap1, key2, pub1) // → layer1
unwrap3 := nip59.Unwrap(unwrap2, key1, pub0) // → original event
----

== What About Type Safety?

The concern was: "Both are *event.Event, how do we know which is wrapped?"

**Answer:** Use the **Kind field**:

[source,go]
----
func IsGiftWrap(e *event.Event) bool {
    return e.Kind == 1059
}

func IsWrapped(e *event.Event) bool {
    return e.Kind == 1059
}

// Usage
if IsGiftWrap(event) {
    inner, err := nip59.Unwrap(event, ...)
    // Recursively check if inner is also wrapped
    if IsGiftWrap(inner) {
        inner2, err := nip59.Unwrap(inner, ...)
        // ...
    }
}
----

== Comparison: Type-Based vs Function-Based

[cols="1,2,2"]
|===
|Aspect |Type-Based (GiftWrap) |Function-Based (Current)

|Recursion
|❌ Breaks meta-circularity
|✅ Maintains meta-circularity

|Simplicity
|❌ More complex (2 types)
|✅ Simple (1 type)

|NOSTR Compliance
|❌ Non-standard abstraction
|✅ Pure NOSTR events

|Multi-layer
|❌ Awkward (unwrap, rewrap)
|✅ Natural (same function)

|Type Safety
|✅ Explicit GiftWrap type
|⚠️ Must check Kind field
|===

== Conclusion

**KEEP the current Event-to-Event design** because:

1. ✅ **Preserves meta-circularity** - can wrap infinitely
2. ✅ **NOSTR-native** - everything is an Event
3. ✅ **Simpler** - one type, not two
4. ✅ **Enables advanced patterns** - onion routing, multi-hop

**DON'T add GiftWrap type** because:

1. ❌ Breaks recursive wrapping
2. ❌ Non-standard abstraction
3. ❌ More complex for no benefit

== The Real Issue in ers-nostr

The problem isn't goNDK's design - it's that **ers-nostr duplicates Event as InnerEvent**.

**Solution:** Replace `InnerEvent` with `*event.Event` everywhere:

[source,go]
----
// BEFORE (ers-nostr)
type InnerEvent struct { ... }  // Duplicate!
func CreateInner(...) (*InnerEvent, error)
func Create(innerEvent *InnerEvent, ...) (*Envelope, error)

// AFTER (use goNDK)
// No InnerEvent type needed!
func CreateInner(...) (*event.Event, error)
func Create(innerEvent *event.Event, ...) (*Envelope, error)
----

This maintains meta-circularity while eliminating duplication.
